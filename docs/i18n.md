# Zweisprachigkeit (Deutsch / Englisch)

Deutsch ist die Standardsprache und liegt ohne Präfix. Englisch liegt unter `/en/`. Astro-i18n-Routing ist **nicht** aktiv, die Routen werden von Hand gepflegt.

## Bausteine

- `src/i18n/index.ts`: einzige Quelle für Routenmap `PAGES` (Schlüssel → Pfad je Sprache), Helfer (`pagePath`, `blogPostPath`, `otherLang`, `langFromPath`, `toLang`, `formatDate`) und das UI-Wörterbuch `ui[lang]` (Navigation, Footer, Blog, 404, Formulare). Die Datei darf nur Typ-Syntax enthalten, die Node ohne Build entfernen kann, weil auch Skripte und Tests sie laden.
- `src/i18n/blog.ts`: Blog-Helfer auf Basis der Collections (`getPosts(lang)`, `englishCounterpart`, `germanOriginal`, `alternateForPost`).
- `src/layouts/BlogLayout.astro`: Props `lang` (Standard `de`), `alternatePath` (Pfad der Gegenseite) und `alternateIsTranslation` (Standard `true`; `false`, wenn `alternatePath` nur ein Ausweichziel ist, dann gibt es keinen hreflang).
- `src/components/LangSwitch.astro`: Umschalter „DE · EN“ samt Cookie-Skript. Wird vom Layout und von `src/pages/index.astro` genutzt.
- `NewsletterForm` und `ContactForm`: Prop `lang`; alle Texte kommen aus `ui[lang]`, die Statusmeldungen des Client-Skripts per `data-msg-*`. Die Formulare senden `lang` mit.
- `lib/i18n.js`: Sprache und Antworttexte der API (`api/*.js` laden nur `lib/`, nicht `src/`).

## Neue Seite übersetzen

1. Die Seite liegt unter dem englischen Pfad aus `PAGES` (z. B. `src/pages/en/hire-an-app-developer.astro`).
2. `<BlogLayout lang="en" alternatePath={pagePath("hire", "de")} …>` bzw. beim eigenen `<html>` (wie `src/pages/index.astro`) `LangSwitch` und die hreflang-Links 1:1 übernehmen.
3. Interne Links immer über `pagePath(key, lang)`. Anker (`#produkte`, `#about`, `#kontakt`, `#newsletter`) behalten ihre deutschen IDs, damit die Layout-Links auf beiden Seiten greifen.
4. Danach `npm run gen:redirects` (siehe unten) und `npm test`.

## Blog

- Deutsche Beiträge: `src/content/blog/<slug>.md`.
- Englische Beiträge: Collection `blogEn`, `src/content/blog-en/<englischer-slug>.md`, gleiches Schema plus Pflichtfeld `translationOf` (= Dateiname/id des deutschen Beitrags ohne Endung).
- Der Sprachumschalter eines deutschen Beitrags ohne Übersetzung zeigt auf `/en/blog/`; dort entsteht kein hreflang.
- Ein englischer Beitrag, dessen `translationOf` auf keinen veröffentlichten deutschen Beitrag zeigt, lässt das Sitemap-/Redirect-Skript mit Fehler abbrechen (kein toter hreflang).
- Solange `blog-en` leer ist, meldet der Glob-Loader beim Build eine Warnung. Das ist erwartet.
- Wird ein Beitrag gelöscht, den ein Build schon kannte, den Cache leeren (`.astro/data-store.json` und `node_modules/.astro/data-store.json` löschen), sonst baut Astro ihn weiter.

## hreflang und Sitemap

- Seiten setzen `hreflang="de"`, `"en"` und `"x-default"` (= deutsche URL) nur, wenn es eine echte Übersetzung gibt.
- Die Sitemap (`astro.config.mjs`) nutzt `@astrojs/sitemap` mit `i18n`-Option. Weil sich die Slugs der Sprachen unterscheiden, setzt `serialize` die Alternativen aus Routenmap und `translationOf` selbst.

## Automatische Sprachweiche

Vercel-Redirects in `vercel.json` (Schlüssel `redirects`), erzeugt von `scripts/gen-lang-redirects.mjs`:

```bash
npm run gen:redirects          # schreibt vercel.json neu
node scripts/gen-lang-redirects.mjs --check   # prüft nur (läuft in tests/i18n.test.mjs und tests/site-build.sh)
```

Regel: Für jede deutsche Einstiegsseite (Startseite, App entwickeln lassen, Ulm, Kosten, Blog-Übersicht und jeden Beitrag mit englischer Übersetzung) gibt es einen 307 auf die englische Entsprechung, wenn

- der Header `Accept-Language` mit `en` beginnt **und**
- kein Cookie `lang` gesetzt ist.

Folgen:

- Crawler ohne `Accept-Language` bleiben deutsch und sehen nie einen Redirect.
- Menschen mit englischer Systemsprache landen beim ersten Besuch auf `/en/`.
- Der Sprachumschalter setzt beim Klick das Cookie `lang=de|en` (1 Jahr, `Path=/`, `SameSite=Lax`). Damit gewinnt die manuelle Wahl dauerhaft; wer „DE“ wählt, wird nie wieder umgeleitet.
- Der RSS-Feed wird bewusst nicht umgeleitet.
- Nur die aufgelisteten Seitenpfade sind Quellen. Assets, `/api/*`, Impressum und Datenschutz sind nicht betroffen. Die CSP- und übrigen Sicherheits-Header bleiben unverändert (der Test `tests/i18n.test.mjs` prüft sie).
- Die Redirects hängen vom Request-Header ab. Das passiert in der Vercel-Routing-Schicht vor dem Cache, deshalb braucht es kein `Vary`.

**Nach jeder neuen englischen Seite oder Übersetzung `npm run gen:redirects` ausführen und `vercel.json` committen**, sonst schlägt der Test fehl.

## API

`api/*.js` lesen `lang` aus Body oder Query (nur `de`/`en`, sonst `de`) und antworten in dieser Sprache: JSON-Meldungen, Bestätigungsmail (Betreff, Text, HTML), Bestätigungsseite. Der Link in der Bestätigungsmail trägt `lang`, das Formular der Bestätigungsseite schickt es zurück. Die interne Mail an Ben (Kontaktformular) bleibt deutsch.

## Rechtliches

`/impressum.html` und `/datenschutz.html` gibt es nur auf Deutsch (rechtsverbindlich). Der englische Footer und die englischen Formulare verlinken sie mit dem Zusatz „(German)“.
